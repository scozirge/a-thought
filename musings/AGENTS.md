# musings 對談與討論紀錄規範

本目錄用來保存 scozirge 與 AI 的隨想、對談與討論紀錄。本文件僅適用於 musings 相關的出題、對談與紀錄工作，以及本目錄和子目錄內的文件；處理這些工作前，Agent 必須先閱讀並遵守本文件。

下文的 `musings/` 路徑皆以 AThought 專案根目錄為基準；若目前工作目錄已是 musings，請直接在目前目錄搜尋及存檔。

## 核心原則

- AI 回答問題時，僅在有助於檢驗論證時提出相關反例與最強反駁，並說明其是否足以動搖原主張；不得為形式上的平衡而捏造、誇大或無關地反對。
- 涉及可查證的事實、研究或會隨時間變動的資訊時，優先查核最新且可靠的資料；清楚區分已知事實、證據強度、AI 的推論與價值判斷，保持客觀。
- 當 scozirge 要求提出一個問題、想法或題目時，AI 必須先快速檢查既有題目，再提供需要理解、推理與可獲得回饋的跨領域題目；詳細做法依下方「出題規則」執行。
- 平常對話以自然、深入的討論為主，不要為了方便歸類而過早替使用者貼上立場或理論標籤。
- scozirge 表達的立場可能隨討論修正。紀錄應完整保留雙方的實質問答過程，而不只保存最後一句結論。
- 文件中一律以 `scozirge` 代稱使用者。AI 回覆者必須標示可驗證的明確模型版本，格式例如 `AI-GPT-5.6 Sol`，不得只寫 `AI`。
- AI 模型名稱必須優先取自目前工作階段可驗證的模型中繼資料，不得依印象或可用模型清單猜測。若只能確認模型家族而無法確認子版本，使用 `AI-Codex（GPT-5 系列，精確子版本未提供）`。
- 若同一份討論跨越不同模型，參與者欄列出所有實際模型，每一輪回答也使用各自的模型標籤；不得用目前模型名稱回頭覆蓋無法驗證的舊回答。
- 清楚區分「scozirge 明確主張」、「AI 的理解或推論」及「仍未回答的問題」。
- 不得把 AI 提出的假設、反例或理論名稱誤寫成使用者已經接受的觀點。
- 預設使用繁體中文，語句以未來容易閱讀、分享及繼續討論為準。
- 討論結束後，關於如何存檔、修改格式、命名文件及管理專案的後設對話，不得收進討論紀錄。

## 出題規則

每當 scozirge 要求「給我一個問題」、「再給我一個想法」或表達相近意思時：

1. **先檢查既有題目**：回答前先快速查看 `musings/` 內現有文件的檔名、文件標題、起始問題標題及續篇標題。原則上只需查看標題；若新題與既有題目看似接近，再讀取相關摘要或起始問題確認是否重複。
2. **避免實質重複**：不可只替換人物、物品或情境，就重問相同的核心問題或使用相同的推理結構。只有在新題加入了足以產生不同推理或答案的新條件時，才可再次觸及相近主題。
3. **主動維持類型多樣性**：優先選擇近期尚未出現或較少出現的領域；若近期題目多為哲學或價值判斷，下一題原則上改用非哲學類型，除非 scozirge 明確指定哲學。
4. **跨領域輪替**：題型應涵蓋但不限於數學、邏輯與悖論、機率與統計、物理、化學、天文、地球科學、生物、心理、歷史、社會、經濟、法律、語言、寫作、程式、工程、地理、音樂、美術、設計及其他適合的領域。不得把列舉項目當成封閉清單。
5. **兼顧可檢驗性**：不要長期只出沒有明確檢驗方式的開放式立場題。應穿插具有較客觀答案、可分析解題過程、可指出錯誤或能提供具體改進建議的題目；避免單純考記憶的冷知識。
6. **標示簡短題名與類型**：每個新題目先標示一個容易辨識的「類型｜題目名稱」，方便之後快速檢查與避免重複。
7. **程式題預設為專業高難度**：scozirge 是專業程式開發者。除非他明確要求基礎題，程式相關問題應直接採高難度，不以基本語法、單一迴圈追蹤或入門除錯作為主要挑戰。題目可輪替進階演算法與資料結構、並行與記憶體模型、分散式系統、資料庫一致性、編譯器、作業系統、網路、安全性、效能分析、架構取捨、測試策略及複雜故障診斷。應明確提供語言、執行環境與必要假設；若未指定技術棧，使用語言中立的虛擬碼或在題目中說明所選環境。重點放在不變量、競態條件、失敗模式、複雜度與設計權衡，不考冷僻 API 或只能靠背誦回答的細節。

## 何時建立紀錄

當使用者表示「存起來」、「做紀錄」、「整理討論」、「最後統整」或相近意思時：

1. 先搜尋 `musings/` 是否已有同一主題的文件。
2. 若是既有主題的延續，優先更新原文件並補上日期；不要建立內容重複的檔案。
3. 若是新主題，建立：

   `musings/討論主題_YYYYMMDD.md`

   日期使用 Asia/Taipei 當地日期及八位數 `YYYYMMDD` 格式。檔名前半部使用能清楚辨識本篇核心內容的繁體中文主題名稱；若包含兩個緊密相關的子題，以半形連字號 `-` 連接，例如：`完美體驗機器-真實性與人生價值_20260728.md`。不得再使用日期在前或英文 topic slug 的命名方式。文件標題使用「討論紀錄｜主題名稱」，讓它與其他類型的文件清楚區隔。

## 紀錄結構

依討論內容調整篇幅，但原則上包含：

1. **文件資訊**：日期、明確主題、參與者與狀態。
2. **起始問題**：最初的問題、情境或爭點。
3. **重要前提**：尤其記錄會大幅影響答案的理想化假設。
4. **scozirge 目前立場**：以忠實、可修正的文字統整。
5. **AI 模型的對照立場**：標示明確模型名稱，只保留有助於看出差異的部分。
6. **共識與分歧**：區分理論條件與現實條件，避免製造不存在的衝突。
7. **相關觀點或理論對照**：僅在確有幫助時加入，並註明「接近」不等於「完全屬於」。
8. **尚待討論**：列出真正未解決的問題，不重複已經回答的問題。
9. **參考資料**：只有實際用到外部資料時才加入。
10. **完整問答過程**：必須放在文件最後，依時間順序完整保留 scozirge 與 AI 的每一則實質發言；此節之後不得再放統整或分析。

整份文件的固定閱讀順序為：

1. 開頭先呈現討論結果統整與摘要。
2. 摘要附近放置真正有助理解的圖表。
3. 中段放前提、立場或理論比較、延伸問題與資料來源。
4. 最後才放完整問答過程，供讀者核對觀點如何形成。

## 簡化標準

- scozirge 的問題、回答、修正及澄清原則上逐則完整保留，不得只留下 AI 的概括。
- scozirge 的原文預設不改寫；只有在他明確指定修改某句時，才以指定的新文字取代。
- AI 模型的實質回覆也必須在「完整問答過程」中完整保留，不可改成摘要，且每一輪都要使用明確模型標籤。
- 文件開頭的統整可以簡化雙方論點，但不得用統整取代文末的完整問答。
- 若 scozirge 下一則發言出現「1／2」、「前者／後者」、「兩種」、「這個問題」、「你提到」或其他指涉語，必須確認前一則完整 AI 回覆包含相應選項、編號、問題或主張，使問答能直接銜接。
- 保留關鍵限定詞，例如「假設完全自願」、「若沒有任何風險」、「在現實世界中」。
- 刪除重複鋪陳，但不可刪到讓結論看似無條件成立。
- 將 AI 過度簡化或後來被修正的說法明確標示為「已修正」，不要當作最後結論。
- 若 scozirge 只表示偏好，不得改寫成道德義務或普遍原則。
- 若 scozirge 說兩個選項都能接受但偏好其中之一，必須分開記錄「可接受範圍」與「偏好排序」。
- 不紀錄工具操作、存檔要求、紀錄格式討論、檔案路徑確認或其他專案管理對話。

## 圖表與格式

- 開頭的討論結果統整原則上附一張真正有助理解的 Mermaid 圖或表格；若主題過於簡單而不適合視覺化，可以省略並說明。
- 圖表必須協助理解內容或推理，不作純裝飾。
- Mermaid 節點文字保持簡短，並使用可在一般 Markdown 閱讀器中顯示的語法。
- 討論紀錄不得依賴 MathJax 或 LaTeX 才能閱讀。不要使用 `\(...\)`、`\[...\]`、`$...$`、`$$...$$` 等數學分隔符，也不要留下 `\rightarrow`、`\frac`、`\times` 等 LaTeX 指令，避免一般 Markdown 閱讀器直接顯示控制符。
- 短公式優先使用一般文字與 Unicode 符號，例如 `P → Q`、`90/585 ≈ 15.38%`、`1% × 90% = 0.9%`。較複雜的計算應使用 Markdown 清單、表格或純文字程式碼區塊逐步呈現。
- 「完整問答過程」若原回覆含有閱讀器不支援的數學標記，可以只轉換顯示語法，不改變原句的實質文字、計算內容與結論。
- 標題與清單不宜過度切碎；整份文件應像一篇可供討論的短文，而不是聊天訊息堆疊。

## 外部資料

- 概念與事實優先引用可靠百科、原始資料、官方資料或學術資料。
- 「目前主流」、「最新調查」等會隨時間改變的內容必須重新查證並標明資料年份。
- 調查結果只能描述受訪群體，不得直接說成全體人類或所有相關領域的共識。
- 引用網路資料時使用可點擊的 Markdown 連結。
