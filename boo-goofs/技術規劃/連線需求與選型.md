# boo-goofs 連線需求與選型

更新日期：2026-09-19。

狀態：需求釐清中。以下區分使用者已確認的需求、技術建議與待確認事項；候選 SDK 尚未透過專案原型驗證，也尚未定案。

## 決策摘要

- **目前首選建議：Photon Fusion 2.1 Host Mode＋Photon Voice，搭配 Steam 身分、好友邀請及雲端存檔。** 先用真實物理搬運、雙人／十人遊玩與語音原型驗證，再鎖定版本和具體物理方案。
- **主開發者時間以 NT$1,000／小時計入機會成本。** 品質先達標，再比較包含實作、整合、除錯、維護在內的總投入；不能僅依服務月費排序。
- **產品目標：Unity PC／Steam、2～10 人合作、公開找房、首發 2～3 張地圖與 BOSS、預計售價 NT$300。** 每天約兩小時，希望一年內完成；另一位負責 3D 資產及 Unity 可用化。
- **已確定的架構邊界：玩家電腦當房主、房主斷線可結束整局、本機／Steam Cloud 存檔、可接受改存檔。** 目前不需要房主遷移、常駐世界或可信的中央經濟後端。
- **主要未決風險：共享物理的具體玩法、語音需求深度、重連／中途加入流程，以及每個 BOSS 需增加多少新系統。** 這些仍會影響實作時間與最終選型。
- **FishNet＋Steam 為備選。** 在既有程式可重用、原型品質、主開發者實際工時或後續總成本明顯更有利時，才重新比較。

## 目前建議

優先驗證 **Photon Fusion 2.1 Host Mode＋Photon Voice**；Steam 負責平台身分、邀請與雲端存檔整合。候選組合需鎖定相容的 Unity、SDK 和範例版本。

這是以整合與除錯時間為重的工程判斷，不代表已證明 Fusion 的連線品質或 AI 實作成功率優於其他框架。

| 功能 | 建議方向 |
| --- | --- |
| 遊戲狀態 | 房主判定怪物 AI、互動歸屬、傷害、BOSS 階段與勝負。 |
| 角色控制 | 評估 Fusion 相容的成熟角色控制器；以飛撲、搬運、倒地與碰撞情境驗收。 |
| 共享物理 | 用實際搬運規格比較 Forecast Physics 與預測／重新模擬方案，尚不指定最終路線。 |
| 公開找房 | 以 Fusion Session／Lobby 作為主要房間目錄，Steam 邀請導向相同遊戲房間。 |
| 語音 | Photon Voice 提供錄音、傳送、播放基礎；聽見誰、面具效果與夢境規則由遊戲實作。 |
| 存檔 | 本機存檔搭配 Steam Cloud，另做版本遷移與衝突處理；存檔歸屬與結算規則待定。 |
| 後端 | 目前沒有必須自建權威經濟伺服器或遊戲伺服器叢集的已確認需求。 |

Fusion 提供多種物理同步策略、Multi-Peer 測試及 Photon Voice 整合。這些工具能否降低本專案的投入，需要實測。[物理方案](https://doc.photonengine.com/fusion/v2/manual/physics/physics-overview)、[Multi-Peer](https://doc.photonengine.com/fusion/v2/manual/testing-and-tooling/multipeer)、[Voice 整合](https://doc.photonengine.com/voice/v2/getting-started/voice-intro)。

Fusion Session 的公開資訊可用於找房與篩選；實際遊戲狀態應使用遊戲同步機制。[房間與配對文件](https://doc.photonengine.com/fusion/v2/manual/connection-and-matchmaking/matchmaking)。Steam Cloud 同步存檔檔案，不代替遊戲內結算或提供可信的中央經濟系統。[Steam Cloud 文件](https://partner.steamgames.com/doc/features/cloud)。

**備選：FishNet＋Steam transport＋成熟語音套件。** 如果既有經驗、物理原型或實際整合工時顯示此組合更合適，則重新比較。開源核心可閱讀與修改，也是除錯優勢；不能僅因其服務月費較低就優先採用。

FishNet 有物理預測工具和 Steam transport；第三方語音整合需驗證版本相容性。[物理預測](https://fish-networking.gitbook.io/docs/guides/features/prediction/predictionrigidbody)、[Steam transport](https://fish-networking.gitbook.io/docs/fishnet-building-blocks/transports/fishysteamworks)、[套件整合](https://fish-networking.gitbook.io/docs/overview/asset-integrations)。

## 新需求對產品設計的影響

### 2～10 人

建議以 2、4、6、10 人作為主要驗收組合，搭配其他人數的基本流程檢查。人數調整需涵蓋合作規則，而不只是怪物血量：

- 收集與同時操作的人力需求，須讓兩人有完成路徑。
- 致盲、禁言、夢境、倒地與救援組合，須避免產生設計外的必敗局面。
- 多人集中打 BOSS 時，驗證攻擊可讀性、音訊混雜、碰撞與技能組合。
- 玩家離開後如何調整難度，以及已取得進度如何處理，需要明確規則。

這些是待驗證的設計事項，尚未改寫原有玩法。

### 公開找房

建議首發驗收包含房間人數／階段／地圖／語言／區域等資訊、版本相容檢查、加入失敗回復、每人音量與靜音，以及房主管理房間的能力。區域資訊不能保證玩家到房主的實際延遲。

是否允許遊戲途中加入、一般玩家斷線重返，以及房主是否能在遊戲中踢人，均需定義。接受修改本機存檔，不等於放棄防止重複互動、錯誤傷害或重複結算等基本一致性檢查。

### 2～3 張地圖與 BOSS

建議共用房間連接規格、互動、狀態效果、怪物感知、語音規則及關卡流程；各關保留自己的核心機制。第一關完成後再依實際工時估算其他關卡。

一年理論工時為 365 × 2＝730 小時，平均每月約 61 小時；這是可投入時間上限，不是已驗證的製作估算，也未計入另一位製作者的工時。構想、整合、測試、商店素材與上架準備都會使用主開發者時間。

## AI 開發流程與選型驗收

1. 先建立正確的角色、互動物件、怪物、狀態效果與語音規則範例，讓後續工作沿用。
2. 以可重建的 Editor 工具與資產檢查減少人工場景設定；與 3D 製作者約定資產交付規格。
3. 為主要狀態記錄輸入、權威判定、切換原因與物件識別，支援可重複的操作腳本。
4. AI 負責實作及可自動驗證的部分；主開發者負責玩法、手感、聲音與恐怖體驗驗收。
5. 衡量每個功能耗費的主開發者時間、介入次數與回歸問題，而非只看 AI 產生多少程式碼。

主開發者工時包含規格溝通、審查、手動編輯、重現問題、調校與驗收。AI 自動執行且不占用主開發者的時間，主要計入工具支出；等待、切換工作或失敗重做實際造成的人工投入仍須記錄。另一位製作者的工時與費用另外計算，不能自動套用主開發者的時薪。

第一個技術原型建議包含少量拼接房間、目標角色控制、真實物理搬運、一種怪物、一個 BOSS 階段及一種語音狀態效果。測試雙人與十人、集中與分散、延遲／抖動／遺失封包，以及房主效能不足等情境。具體數量、網路條件與通過門檻尚待需求補齊。

Multi-Peer 可協助快速重現遊戲狀態問題；實際跨網路連線、Steam 邀請、真人語音與目標硬體效能須另外驗證。

## 時間成本與選型方法

使用者指定的 **NT$1,000／小時**是決策用的機會成本，不代表每個開發小時都會真的損失同額正職收入，也不是必須支付出去的現金。後續估算需同時列出現金支出與包含時間價值的經濟成本。

| 投入時間 | 機會成本 | 對目前開發節奏的意義 |
| --- | ---: | --- |
| 2 小時 | NT$2,000 | 約一天可投入的開發時間 |
| 10 小時 | NT$10,000 | 約五天的開發時間 |
| 30 小時 | NT$30,000 | 約十五天的開發時間 |
| 60 小時 | NT$60,000 | 約一個月的開發時間 |
| 730 小時 | NT$730,000 | 全年每天投入兩小時的理論上限 |

平均每月約 60.8 小時，對應約 NT$60,833 的時間價值。上述數字反映投入能力與價值，並非已承諾的製作工期。

比較流程：

1. 先檢查方案能否符合玩家房主制、2～10 人、操作手感、物理互動、語音及穩定度等必要要求。
2. 對通過品質門檻的方案，估算實作、整合、除錯、驗收、升級與維護占用的主開發者工時。AI 帶來的節省以實際少用的人工時間計算。
3. 使用相同評估期間與相同玩家量／遊玩時數假設，比較現金支出和總經濟成本；可採「開發期＋上市後 12 個月」為一個情境。
4. 將尚未驗證的工時列成範圍，標示哪些數據來自原型、哪些仍是推估；上市提早或延後的營收影響另列情境，避免和工時價值重複計入。

```text
方案總經濟成本
= 主開發者總工時 × NT$1,000
+ 工具、SDK、支援與 AI 使用費
+ 同一評估期間的服務／流量支出
+ 其他人力及必要支出

在品質同樣達標時，付費方案的時間價值優勢
= 實際節省的主開發者工時 × NT$1,000 − 相對增加的總現金支出
```

例如：若某組付費工具確實省下 60 小時，對應 NT$60,000 的時間價值。若與另一方案相比，接下來 12 個月每月多支出 NT$5,000，則這部分剛好相抵；更長期仍需持續計入月費及維護差異。這是比較方法，不表示已證明 Fusion 能省 60 小時。

因此可優先評估成熟控制器、語音套件、除錯工具、技術支援及 AI 自動驗證流程。每項採購仍應有要節省的具體工作與驗收方式，不把「付費」直接視為更高品質或更省時間。

## 營收與服務費用估算

先滿足品質與實作時間需求，再比較總支出；計入開發與維護占用的時間。CCU 反映使用量，買斷制仍需分開估算新銷售與既有玩家的持續遊玩。

目前價格例：Fusion 1,000 CCU 為 US$250／月，Voice 1,000 CCU 為 US$185／月，合計 US$435／月。以預算匯率 35 計約 NT$15,225；超額流量等另計。先前討論的 NT$30,000／月是留有餘裕的規劃值，不是帳單上限，也不代表現在就需訂購。[Fusion 價格](https://www.photonengine.com/fusion/pricing)、[Voice 價格](https://www.photonengine.com/voice/pricing)。

若假設每份有效實收 NT$180，NT$30,000／月約需 167 份銷售支應，一年 NT$360,000 約需 2,000 份。實收 NT$180 只是情境假設；此計算只涵蓋上述連線預算，不是整款遊戲的損益平衡點。

把時間加入的一個獨立情境：假設開發期實際投入 730 小時，上市後第一年連線預算持續為每月 NT$30,000，則這兩項經濟成本合計 NT$1,090,000；以每份實收 NT$180 計，約 6,056 份銷售可支應這兩項。此情境未計 3D、其他工具、人力、行銷與上市後維護工時，且不假設遊戲一上市就有 1,000 CCU；不得將其當成銷量預測、現金需求或完整損益平衡點。

## 供後續評估沿用的原則

- 使用者技術能力充足；重點是有限時間內的交付效率、品質與 AI 可獨立完成及驗證的程度。
- 服務成本在品質與開發效率達標後再比較；高 CCU 可支持較大的營運投入，但需分開估算新銷售收入與既有玩家的持續使用。
- 維持使用者已確認的首發 2～3 關與公開找房目標。第一關技術驗證不等於將首發範圍縮成只有一關。
- 房主遷移不列為必要功能或選型加分理由；一般玩家的重連則仍待確認。
- 每次比較 SDK／套件，列出要驗證的具體玩法、估計節省工時、新增現金支出與相容性證據。
- 決策文件中的「建議」及「待確認」不得自動視為使用者已同意；既有玩法發想也不代表全部納入首發。

## 待確認事項

已提出、尚待回答：

- 是否多人同時搬同一件物品、搬運玩家的具體方式、投擲／撞擊傷害是否依重量與速度，以及同時活動物件的大概數量。既有玩法紀錄包含搬玩家，正式實作規格仍待確認。
- 單局時間；是否允許一般玩家重返原局，以及新玩家中途加入。
- 語音是否只包含距離、遮擋與狀態規則，或還包含麥克風音量引怪、錄下／模仿玩家聲音。

後續收斂所需：

- 主要玩家地區、語言與跨區組隊的目標體驗。
- 個人解鎖、裝備與隊伍戰役進度的存檔歸屬；中途離開、被踢與房主斷線時的結算。
- 現有 Unity 程式／版本、最熟悉或已有可重用程式的連線框架。
- 首發各地圖／BOSS 的核心差異、共用怪物與道具量。
- 目標硬體、解析度與幀率，以及 3D 資產交付是否包含綁定、動畫、碰撞和 LOD 等。
